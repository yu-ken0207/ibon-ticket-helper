# 一般票券訂票助手（ibon-ticket-helper）

Chrome 擴充功能（MV3），給一般票券（例如游泳池單次入場票）用的購票輔助：照你的偏好選時段、填各票種張數、填你提供的購票人資料，**停在確認頁**，由你自己檢查後按確認。遇到排隊、驗證碼、機器人檢查一律停下來交給你，不會略過，也不會碰。

> **目前狀態**：只支援本機的一般票券模擬站（[ticket-sim](../ticket-sim/) 用 `SIM_SITE=pool` 啟動），**還沒有接任何真實網站，包括 ibon**。接真實網站之前，要先確認該票券的法律適用、網站服務條款與允許的自動化方式；依文化創意產業發展法第 10-1 條與運動產業發展條例第 24 條之 1，演唱會、藝文表演、運動賽事的票券不在使用範圍內。

這個專案是從 [KKTIX 訂票助手](../kktix-booking-helper/)拆出來的（2026-10-15）：架構相同（背景程式排程、頁面程式做每一步、設定頁），KKTIX 助手仍然只處理 KKTIX。

---

## 一、安裝

1. Chrome 網址列輸入 `chrome://extensions`，打開右上角的「開發人員模式」。
2. 按「載入未封裝項目」，選這個資料夾。`test/` 只是測試用，不影響擴充功能。

## 二、用法

1. 啟動模擬站：在 `../ticket-sim` 執行 `npm run start:pool`，網址是 `http://127.0.0.1:3300/pool/`。到 `/pool/scenarios` 可以切換情境（尚未開賣、售完、503、排隊、驗證碼…），每個情境都有「困難模式」（見第六節）。
2. 打開擴充功能，填：
   - **網址**：`http://127.0.0.1:3300/pool/`
   - **時段關鍵字**：一行一組，越上面越優先，例如「11/20 06:00」。同一行用空格隔開，每一段都要出現在時段文字裡。只寫一個時間代表開始時間；破折號（–、-、～）都當成一樣。
   - **票種與張數**：一行一筆，例如「全票 2」「兒童票 1」，名稱照網站上的寫法。
   - **購票人資料**：姓名、手機、Email、備註（選填）。只存在這台電腦，匯出紀錄時會隱藏；開始前會檢查有沒有填完整、格式對不對。
   - **自動勾選同意使用須知**：關掉的話，填好資料就停下來讓你自己勾。
3. 「**檢查時段**」會在背景讀時段狀態與票價，告訴你開賣時會選哪一個；「**健檢**」檢查時段列表頁還是不是助手認得的樣子。兩者都不會選購。
4. 「**排程**」（設定開賣時間）或「**立即執行**」。它會選時段、填張數與資料，停在確認頁，標出「確認建立訂單」，由你自己按。
5. 停下來交給你之後（排隊、資料有問題…），你處理好了，按「**繼續**」讓它從目前這一頁接著做。

紀錄旁的「**匯出**」會把任務、紀錄、黑盒子存成 JSON 檔；購票人資料不會被匯出。

## 三、它會做、不會做

| 狀況 | 行為 |
|---|---|
| 時段尚未開放 | 按「更新狀態」重看，間隔與次數照進階設定 |
| 偏好的時段額滿、剩的不夠 | 換下一組偏好；都不行就停下來說明。開了遞補才會改選其他能買的時段 |
| 送出時剛好被買走 | 記下這個時段，回列表改選下一組偏好 |
| 讀取失敗（503 等） | 按「更新狀態」重試，間隔逐步拉長，連續 5 分鐘都失敗才交給你 |
| 錯誤頁（500） | 重新整理，上限同上 |
| 送出時伺服器錯誤 | 確定失敗了才再送一次，次數照「送出失敗後重送幾次」 |
| 表單過期（網站說權杖過期） | 重新整理這一頁拿新的權杖，這一步重做一次；次數同上 |
| 回應很慢 | 送出後最多等 60 秒，不會因為等太久又按一次 |
| 重複送出 | 同一步只按一次；網站說重複時不再送，直接往下一步看 |
| 購票人資料不完整 | 開始前就擋下並說明缺什麼，不開任何頁面 |
| 網站說資料有問題 | 照網站逐欄的訊息停下來交給你 |
| 確認頁 | 一定停下來，不會按「確認建立訂單」；保留剩 1 分鐘、到期都會提醒 |
| 排隊、驗證碼、機器人檢查 | 停下來交給你，不會略過，也不會碰驗證碼或替你點「我不是機器人」；排程倒數時遇到排隊也一樣。處理完按「繼續」，它從目前這一頁接著做 |
| 頁面在背景 | 開賣前 25 秒背景程式叫醒自己，頁面計時器被 Chrome 拖慢時由背景程式補重新整理 |

## 四、程式結構

| 位置 | 內容 |
|---|---|
| `lib/flow.js` | 通用的流程判斷：選時段、配票種張數、檢查購票人資料、網站錯誤該重試／換時段／停下來。不碰網頁，單元測試直接測 |
| `lib/sites.js` | 支援哪些網站、網址規則 |
| `lib/` 其他 | 重試間隔、對時計算、健檢摘要、黑盒子整理、格式化 |
| `src/agent/` | 頁面程式：核心、語意定位（`05-dom.js`）、網站轉接（`10-pool.js`，唯一知道模擬站頁面長什麼樣子的地方）、面板、對時、流程、黑盒子、啟動 |
| `agent.js` | 由 `tools/build.mjs` 把 `src/agent/` 串起來、內嵌 `lib/` 產生，跑在 ISOLATED world。不要直接改它 |
| `background.js` | 背景程式：排程、到點保險、任務狀態、重試額度、通知、「繼續」、黑盒子 |
| `popup.*` | 設定頁 |

## 五、新增一個網站

1. **先確認該網站與票券的法律適用、服務條款、允許的自動化方式。** 演唱會、藝文表演、運動賽事的票券不做。
2. 在 `lib/sites.js` 登記網址規則。
3. 照 `src/agent/10-pool.js` 寫一支轉接，提供同樣的函式：頁面種類、時段列表、選購、票種與張數、購票人欄位、確認頁的關卡、錯誤訊息。流程（`60-flow.js`、`lib/flow.js`）不用改。
   定位只用畫面上看得到的文字、欄位標籤、網址、表單欄位名稱（`05-dom.js` 的工具），不要依賴網站內部的 class、id；這些很容易改版就換掉。
4. 在 `manifest.json` 加上那個網站的網址，並在模擬站補對應的情境與測試，一般模式和困難模式都要通過。

## 六、測試

```bash
node tools/build.mjs                  # 改了 src/agent/ 或 lib/ 之後，重新產生 agent.js
node --test 'test/unit/*.test.mjs'    # 單元測試 13 個，不到一秒
node test/run-tests.mjs               # 端對端 18 個情境 × 一般／困難兩種模式，約 4 分鐘；需要 ../ticket-sim（可用 SIM_DIR 指定）
node test/run-tests.mjs --only happy,queue --mode hard   # --mode normal|hard|both，預設 both
```

端對端測試會啟動模擬站、讓 Chromium 載入真的擴充功能，每個情境除了看任務狀態，也用模擬站的統計核對：沒有重複送出、沒有替使用者按「確認建立訂單」。Playwright 預設從 `../ticket-sim/tools` 載入，可用 `PW_DIR` 指定。

情境：正常流程（停在確認頁、使用者確認後才建立訂單）、排程與開賣前預告、售完、送出時剛好被買走、剩少量、503、500 錯誤頁、送出時伺服器錯誤、表單權杖過期、回應很慢、保留逾時提醒、驗證碼、機器人檢查、排隊（含排程倒數時遇到）、網站說資料有問題、購票人資料不完整、檢查時段與健檢。

### 困難模式

模擬站開情境時加 `hard=1`（情境頁的「困難模式」連結），把真實售票網站常見的技術難點做進去。每個端對端情境都會在一般模式和困難模式各跑一次，同一支轉接要兩邊都過。

| 困難模式的難點 | 助手怎麼處理 |
|---|---|
| 沒有 `data-testid`；網站自己用的屬性名稱、元素 id、購票人欄位的 `name` 每次產生頁面都隨機換，也沒有 `autocomplete` | 用看得到的文字、欄位標籤（`label.control`）、網址定位 |
| 時段列表放在封閉的 Shadow DOM 裡，網頁的程式讀不到 | 用擴充功能才有的 `chrome.dom.openOrClosedShadowRoot` 讀 |
| 受控表單：網站以自己的資料模型為準，只改欄位的值、沒有送出事件，網站不會認 | 用原生的 value setter 設值，再送出 `input`、`change` 事件 |
| 送出要帶頁面發的表單權杖，過期就被拒絕（`tokenSec` 調時效；情境 `token-expired` 讓第一次送出一定過期） | 重新整理拿新的權杖，這一步重做一次，有次數上限 |
| 驗證碼畫在 canvas 上 | 認得出是驗證碼，停下來交給你，不讀也不填 |
| 時段列表延遲 0.3～1.5 秒才出現，只有「載入中」佔位列，沒有 `aria-busy` | 等佔位列消失、而且是新的一批時段才讀，不會讀到更新前的舊資料 |
