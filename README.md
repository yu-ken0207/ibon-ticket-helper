# 一般票券訂票助手（ibon-ticket-helper）

Chrome 擴充功能（MV3），給一般票券（例如游泳池單次入場票）用的購票輔助：照你的偏好選時段、填各票種張數、填你提供的購票人資料，**停在確認頁**，由你自己檢查後按確認。遇到排隊、驗證碼、機器人檢查一律停下來交給你，不會略過，也不會碰。

> **目前狀態**：選購流程由購票流程引擎（第四節）驅動，只在本機的一般票券模擬站自動執行（[ticket-sim](../ticket-sim/) 用 `SIM_SITE=pool` 啟動）。**ibon 的活動頁與購票頁只讀取資訊、比對你的需求**（場次、票價、開賣時間、限購、頁面狀態，見第四節）；在 ibon 上點選、送出、驗證碼、付款都由你自己做。接真實網站之前，要先確認該票券的法律適用、網站服務條款與允許的自動化方式；依文化創意產業發展法第 10-1 條與運動產業發展條例第 24 條之 1，演唱會、藝文表演、運動賽事的票券不在使用範圍內。

這個專案是從 [KKTIX 訂票助手](../kktix-booking-helper/)拆出來的（2026-10-15）：架構相同（背景程式排程、頁面程式做每一步、設定頁），KKTIX 助手仍然只處理 KKTIX。

---

## 一、安裝

1. Chrome 網址列輸入 `chrome://extensions`，打開右上角的「開發人員模式」。
2. 按「載入未封裝項目」，選這個資料夾。`test/` 只是測試用，不影響擴充功能。
3. **更新程式之後**（`git pull` 或改了程式）：
   - 在這個資料夾執行 `node tools/build.mjs --check`，確認 `agent.js`、`ibon-info.js` 跟原始碼一致（不一致就先執行 `node tools/build.mjs`）。
   - 到 `chrome://extensions` 找到「一般票券訂票助手」，確認「載入來源」是這個資料夾，按重新載入（↻），卡片上的版本要變成新的版本。
   - 關掉再打開設定頁，標題旁會顯示版本（例如 `v0.3.1`）。
   - 已經開著的網站分頁要重新整理，新的頁面程式才會載入到那一頁。

## 二、用法

1. 啟動模擬站：在 `../ticket-sim` 執行 `npm run start:pool`，網址是 `http://127.0.0.1:3300/pool/`。到 `/pool/scenarios` 可以切換情境（尚未開賣、售完、503、排隊、驗證碼…），每個情境都有「困難模式」（見第六節）。
2. 打開擴充功能，填：
   - **網址**：`http://127.0.0.1:3300/pool/`
   - **時段關鍵字**：一行一組，越上面越優先，例如「11/20 06:00」。同一行用空格隔開，每一段都要出現在時段文字裡。只寫一個時間代表開始時間；破折號（–、-、～）都當成一樣。
   - **我的需求**：
     - **票種與張數**：一行一筆，例如「全票 2」「兒童票 1」，名稱照網站上的寫法。
     - **票區偏好**（選填，有分區的網站才用）：一行一組，越上面越優先；沒填就照頁面順序。
     - **最高單價、總金額上限**（選填）：超過就不選；都不符合就停下來說明，不送出選購。
     - ibon 的唯讀比對也用這一份需求。
   - **購票人資料**：姓名、手機、Email、備註（選填）。只存在這台電腦，匯出紀錄時會隱藏；開始前會檢查有沒有填完整、格式對不對。
   - **自動勾選同意使用須知**：關掉的話，填好資料就停下來讓你自己勾。
3. 「**檢查時段**」會在背景讀時段狀態與票價，告訴你開賣時會選哪一個；「**健檢**」檢查時段列表頁還是不是助手認得的樣子。兩者都不會選購。
4. 「**排程**」（設定開賣時間）或「**立即執行**」。它會選時段、填張數與資料，停在確認頁，標出「確認建立訂單」，由你自己按。
5. 停下來交給你之後（排隊、資料有問題…），你處理好了，按「**繼續**」讓它從目前這一頁接著做。正在選購時可以按「**暫停**」：做完手上這一個檢查就停，不再做新的操作。
   任務區會顯示目前的流程狀態、場次與票區的候選和理由、交接內容（為什麼停、停在哪、已確認的內容、你要做的下一步），以及流程紀錄。
6. **ibon 活動頁**：網址貼 `https://ticket.ibon.com.tw/ActivityInfo/Details/數字`，按「**讀取活動資訊**」。排程、立即執行、檢查時段、健檢會停用，原因寫在按鈕下方（見第四節）。
7. 網址還沒填、或不是支援的網站時，排程、立即執行、檢查時段、健檢都會停用，按鈕下方寫原因。能不能按跟背景程式接不接受任務是同一個判斷；其他欄位（時段、票種、購票人資料）按下去才檢查，並說明缺什麼。

紀錄旁的「**匯出**」會把任務、紀錄、黑盒子存成 JSON 檔；購票人資料不會被匯出。

## 三、它會做、不會做

| 狀況 | 行為 |
|---|---|
| 時段尚未開放 | 按「更新狀態」重看，間隔與次數照進階設定 |
| 偏好的時段額滿、剩的不夠 | 換下一組偏好；都不行就停下來說明。開了遞補才會改選其他能買的時段 |
| 送出時剛好被買走 | 記下這個時段，回列表改選下一組偏好 |
| 讀取失敗（503 等） | 按「更新狀態」重試，間隔逐步拉長，連續 5 分鐘都失敗才交給你 |
| 讀取時網站說請求太多（429） | 照網站給的 `Retry-After` 等了才再讀（回應標頭由背景程式看）；沒給就等 2、4、8 秒。最多重試 3 次；試完還是 429，或網站要等超過 2 分鐘，就交給你 |
| 送出時網站說請求太多（429） | **不自動重送**，停下來交給你；你自己按，或按「繼續」才會再送 |
| 網站的錯誤訊息沒寫狀態碼 | 一樣認得 429：出錯時會問背景程式剛剛的回應狀態，不只看頁面上的字 |
| 錯誤頁（500） | 重新整理，上限同上 |
| 送出時伺服器錯誤 | 確定失敗了才再送一次，次數照「送出失敗後重送幾次」 |
| 表單過期（網站說權杖過期） | 重新整理這一頁拿新的權杖，這一步重做一次；次數同上 |
| 回應很慢 | 送出後最多等 60 秒，不會因為等太久又按一次 |
| 重複送出 | 同一步只按一次；網站說重複時不再送，直接往下一步看 |
| 購票人資料不完整 | 開始前就擋下並說明缺什麼，不開任何頁面 |
| 網站說資料有問題 | 照網站逐欄的訊息停下來交給你 |
| 確認頁 | 一定停下來，不會按「確認建立訂單」；保留剩 1 分鐘、到期都會提醒 |
| 排隊、驗證碼、機器人檢查 | 停下來交給你，不會略過，也不會碰驗證碼或替你點「我不是機器人」；排程倒數時遇到排隊也一樣。處理完按「繼續」，它從目前這一頁接著做 |
| 頁面在背景 | 開賣前 25 秒背景程式叫醒自己，頁面計時器被 Chrome 拖慢時由背景程式補重新整理 |
| 偏好的票區售完 | 換下一個符合偏好、預算、張數的票區；送出時才售完也一樣（記下這個票區，重新整理選票頁再選） |
| 超過最高單價或總金額上限 | 跳過那個票區或場次；都不符合就停下來說明，不送出選購 |
| 偏好的場次狀態看不出來 | 不猜，也不當成還沒開放一直重看，停下來請你確認 |
| 網站說登入逾時 | 停下來請你重新登入，再按「繼續」 |
| 送出結果不明（連線中斷、逾時） | **不重送**，停下來請你看頁面或訂單查詢確認 |
| 確認頁的內容跟計畫不一致 | 不交接付款，停下來列出哪裡不一樣（場次、票區、張數、金額） |
| 重新整理、按上一頁、按「繼續」 | 已經做完的步驟（保留名額、送出購票人資料）不重做；已經保留了又回到列表，會停下來而不是再選一次 |
| 背景程式（service worker）被 Chrome 收掉 | 流程狀態存在 storage，重新叫醒後接著用 |

## 四、購票流程引擎

決策和網站操作分開，每個網站操作執行前都要過政策檢查：

| 部分 | 程式 | 做什麼 |
|---|---|---|
| RequirementMatcher、PurchasePlanner | `lib/planner.js` | 需求對場次、票區、票種、價格、限購；排出候選並寫明每一個選或不選的理由；核對確認頁（`reviewOrder`）。不碰網頁 |
| WorkflowEngine | `lib/workflow.js`（規則）＋ `background.js` 的 `onWf`（執行） | 下表的狀態與轉移；不合法的轉移、被暫停或取消時不准往下做 |
| WorkflowStateStore | `task.wf`（chrome.storage） | 目前狀態、歷程（最多 60 筆）、做完的步驟、這次的選擇、規劃、試過買不到的票區；重新整理、service worker 重啟後接著用 |
| SiteAdapter | `src/agent/10-pool.js`（模擬站，可操作）、`src/info/20-adapter.js`（ibon，只讀） | 認頁面、讀狀態、執行網站允許的操作 |
| PolicyGate | `lib/policy.js` ＋ `background.js` 的 `onGate` | 每個操作前問：`ALLOWED` 才做；`CONFIRMATION_REQUIRED`、`BLOCKED`、`UNKNOWN` 都停下來交給你 |
| HandoffManager | `lib/workflow.js` 的 `composeHandoff` ＋ 設定頁 | 交給你時整理原因、目前頁面、已確認的內容、下一步 |

**流程狀態**（`lib/workflow.js` 的 `STATES`；暫停、取消、失敗、交給你另外統一處理：助手在做事時都可以轉過去，交給你和暫停之後按「繼續」回到判斷頁面）：

| 狀態 | 進入條件 | 網站操作（每一個都過 PolicyGate） | 完成條件 | 錯誤處理與下一步 |
|---|---|---|---|---|
| `IDLE` 尚未開始 | 沒有任務 | — | 你按「立即執行」或「排程」 | — |
| `WAITING_FOR_SALE` 等待開賣 | 排程後到開賣前；或時段還沒開放、還在重看次數內 | `read-page`、`refresh-list` | 開賣時間到（頁面倒數與背景到點保險），或頁面顯示已開放 | 重看次數用完 → FAILED；遇到排隊 → QUEUE_HANDOFF |
| `PAGE_DETECTION` 判斷目前頁面 | 每次頁面載入、開賣重新整理後，或你按「繼續」 | `read-page` | 認出是哪一頁 | 認不得 → MANUAL_CONFIRMATION |
| `ACTIVITY_READ` 讀取活動與場次 | 在場次列表頁 | `read-page`、`refresh-list` | 讀到場次、狀態、票價 | 讀取失敗照重試額度重讀；429 照 Retry-After；一直讀不到 → MANUAL_CONFIRMATION |
| `REQUIREMENT_CHECK` 比對你的需求 | 讀到場次與票價 | — | 有符合需求的場次（依偏好排序，附理由） | 尚未開放 → WAITING_FOR_SALE；偏好的場次狀態看不出來 → MANUAL_CONFIRMATION；沒有符合的（售完、預算、張數）→ FAILED |
| `SESSION_SELECTION` 選場次 | 規劃出要選的場次 | `select-session` | 進到選票頁 | 找不到選購按鈕 → MANUAL_CONFIRMATION；你已經保留了名額 → MANUAL_CONFIRMATION（不重選） |
| `TICKET_AREA_SELECTION` 選票區與票種 | 在選票頁 | `select-area` | 選好符合偏好、預算、張數的票區（沒有分區就只對票種） | 這一步已經做過（已保留）→ 直接往下一頁，不重送；沒有符合的票區 → FAILED；選不起來 → MANUAL_CONFIRMATION |
| `QUANTITY_SELECTION` 選張數並送出選購 | 票區、票種已決定 | `set-quantity`、`submit-hold` | 網站接受選購，進到下一頁 | 售完 → 換下一個票區或場次；伺服器錯誤（確定失敗）照次數上限重送；結果不明（連線中斷、逾時）→ MANUAL_CONFIRMATION，不重送；429 → RATE_LIMIT_HANDOFF；登入逾時 → MANUAL_CONFIRMATION |
| `BUYER_INFO` 填購票人資料 | 在購票人資料頁（選購已保留） | `fill-profile`、`agree-terms`、`submit-buyer` | 網站接受資料，進到確認頁 | 資料不完整或網站說哪一欄有問題 → MANUAL_CONFIRMATION；不自動勾同意 → MANUAL_CONFIRMATION；結果不明 → MANUAL_CONFIRMATION |
| `ORDER_REVIEW` 核對訂單 | 在確認頁 | `read-page` | 確認頁的場次、票區、張數、金額跟計畫一致 | 不一致 → MANUAL_CONFIRMATION |
| `QUEUE_HANDOFF` 排隊中：交給你 | 遇到排隊或等候室 | — | 你按「繼續」 | — |
| `CHALLENGE_HANDOFF` 驗證：交給你 | 遇到驗證碼、機器人檢查或其他驗證 | — | 你自己完成驗證後按「繼續」 | — |
| `RATE_LIMIT_HANDOFF` 請求太多：交給你 | 送出遇到 429，或讀取重試用完 | — | 你等一下後按「繼續」 | — |
| `MANUAL_CONFIRMATION` 需要你確認 | 資料不完整、登入逾時、結果不明、狀態看不出來、內容不一致、認不得的頁面 | — | 你處理後按「繼續」 | — |
| `PAYMENT_HANDOFF` 付款前交接 | 確認頁核對無誤 | — | 你自己按「確認建立訂單」、付款；完成頁出現 → COMPLETED | 保留快到期、到期都提醒 |
| `PAUSED` 已暫停 | 你按「暫停」 | — | 你按「繼續」 | — |
| `FAILED` 沒有完成 | 沒有符合需求的選擇，或錯誤用完重試 | — | — | — |
| `COMPLETED` 完成 | 你確認後網站建立了訂單 | — | — | — |
| `CANCELLED` 已取消 | 你按「取消任務」、分頁被關掉，或被新任務取代 | — | — | — |

**操作政策**（`lib/policy.js`）：模擬站的選場次、選票區、選張數、送出選購、填資料是 `ALLOWED`；自動勾同意照你的設定；「確認建立訂單」是 `CONFIRMATION_REQUIRED`（不可逆，一定由你按）；驗證碼、略過排隊、付款是 `BLOCKED`；沒列在表上的操作與認不得的網站是 `UNKNOWN`。ibon 照下一節的 `IBON_POLICY`：只讀是 `ALLOWED`，選擇、張數、送出、重新整理都是 `CONFIRMATION_REQUIRED`，驗證、排隊、限購、付款是 `BLOCKED`，所以引擎在 ibon 上不會執行任何網站操作。

## 五、ibon：只讀取與比對（IbonAdapter）

ibon 的整合分成「網站辨識、頁面轉接、操作政策、任務」四塊一起設計，不是把 ibon 加進 `siteOf()` 就算支援：

| 部分 | 程式 | 現況 |
|---|---|---|
| 網站辨識 | `lib/ibon.js` 的 `ibonPageKind()` | 活動頁、「線上購票」轉址、購票流程入口 `orders.ibon.com.tw/application/UTK02/UTK0201_000.aspx`（網址是從真站資料解出來的）、購票流程其他頁 |
| 頁面轉接 | `src/info/20-adapter.js` 的 `IbonAdapter`（跟模擬站的 `POOL` 分開） | `pageKind`、`readActivity`、`loginState`、`readState`、`supportedActions`、`snapshot`；**沒有點擊、填值、送出的函式** |
| 操作政策 | `lib/ibon.js` 的 `IBON_POLICY` | 每種操作「助手會做／你自己做／不做」與條款依據，設定頁照實顯示 |
| 任務 | `siteOf()` 不認 ibon | 排程、立即執行、繼續、檢查時段、健檢一律不接受 ibon 網址 |

**設定頁能做的（都只讀）**
- **讀取活動資訊**：網址欄貼活動頁。已經開著同一頁就直接讀，沒有的話在背景開一個分頁讀完就關。讀活動名稱、售票平台、場次（演出時間、場地、狀態、截止時間）、節目介紹裡的票價與開賣時間、購票須知裡的限購、登入狀態（頁首有「快速登入」＝沒登入）。場次表在網站的**封閉 Shadow DOM** 裡，用擴充功能的 `chrome.dom.openOrClosedShadowRoot` 讀。
- **資料檢查**：場次缺漏、看不出狀態、全部售完、已過截止、開賣時間還有幾天、票價缺漏。
- **跟「我的需求」比對**：用設定頁的票區偏好、票種張數的合計、最高單價。比對節目介紹的票價表，張數比對「每位會員限購 N 張」（身障、陪同、周邊商品的規定不算）。只比對，不會替你選。
- **讀取目前的 ibon 分頁**：在活動頁或購票頁時按，看這一頁是什麼頁、有沒有登入、頁面上有沒有售完、排隊、驗證碼、錯誤這類字樣（購票頁一律標「未驗證」）。
- **記錄結構快照**：在購票頁按，把頁面結構（含封閉 Shadow DOM）存成檔案，給開發「購票頁讀取」用。遮掉 Email、手機、身分證、6 碼以上的數字、「XXX 您好」與「購票人／姓名／會員…：XXX」後面的名字，以及你在「購票人資料」填的姓名、手機、Email；網址只留參數名稱，文字輸入欄只記「有沒有填」，選項記值與有沒有被選。存檔前再掃一次，還找得到 Email、手機、身分證、長數字或你的資料就**不存檔**，只告訴你找到哪一類。沒有規則可循的名字（例如單獨出現的姓名）仍可能留著，交出去之前請打開看過。
- **開始人工操作模式**：網址欄貼活動頁、填好需求後按。助手只讀頁面：活動頁給建議（先登入、該按哪一列的「線上購票」）與判斷依據（每個場次選或不選的理由、需求比對、為什麼由你做）；你自己操作換頁後，助手讀新的一頁、核對上一步，並列出每個欄位是「讀取成功」「讀取失敗」「尚未驗證」還是「這一頁沒有」。到了「填寫購票資訊」（UTK0206，第 4 步）會讀出場次時間、場地、座位、票種、單價、張數、總計、保留剩餘時間、電話有沒有填（不讀內容）、付款與取票方式、同意有沒有勾，並核對場次時間跟活動頁的建議、張數與票種跟需求、單價與總額跟預算，不一致就提醒（要不要取消由你決定）。其他購票頁還沒取得真站快照，票區、價格、剩餘、張數一律「尚未驗證」，不猜；驗證碼只辨識有沒有，不讀、不填。用「取消任務」結束。

**在 ibon 上，網站的操作一律由你自己做**（`IBON_POLICY`，依服務條款 https://ticket.ibon.com.tw/NewsInfo/Details/348）：

| 操作 | 處理 | 依據 |

**限制**
- 票區與票價是節目介紹裡寫的；實際能買的票區、剩餘數量在購票流程裡，購票頁的結構還沒在真站看過（需要你用結構快照提供）。
- 真站核對過的只有：活動頁的結構與場次表、「線上購票」「已售完」兩種按鈕字、場次小字「…截止」、沒登入時頁首的「快速登入」（活動 39972，2026-10-15）。填寫購票資訊頁（UTK0206）2026-10-16 用一次結構快照核對過。「尚未開賣」等字、「…開賣」小字、活動頁登入後的頁首、購票流程第 1～3、5 步、排隊頁都還沒看過。
- 讀法依賴目前的頁面結構（`<app-game>` 裡的 `#GameInfoList`、說明區塊的標題）。讀不到時會照實說，不會猜。

## 七、新增一個網站

1. **先確認該網站與票券的法律適用、服務條款、允許的自動化方式。** 演唱會、藝文表演、運動賽事的票券不做選購。只讀取活動資訊（A 類）可以先做，像 ibon 那樣放在 `lib/sites.js` 的 `INFO_SITES`，不要放進 `SITES`。
2. 在 `lib/sites.js` 登記網址規則。
3. 照 `src/agent/10-pool.js` 寫一支轉接，提供同樣的函式：頁面種類、時段列表、選購、票種與張數、購票人欄位、確認頁的關卡、錯誤訊息。流程（`60-flow.js`、`lib/flow.js`）不用改。
   定位只用畫面上看得到的文字、欄位標籤、網址、表單欄位名稱（`05-dom.js` 的工具），不要依賴網站內部的 class、id；這些很容易改版就換掉。
4. 在 `manifest.json` 加上那個網站的網址，並在模擬站補對應的情境與測試，一般模式和困難模式都要通過。

## 八、測試

```bash
node tools/build.mjs                  # 改了 src/ 或 lib/ 之後，重新產生 agent.js 和 ibon-info.js
node --test 'test/unit/*.test.mjs'    # 單元測試 58 個，不到一秒
node test/run-tests.mjs               # 端對端：模擬站 25 個情境 × 一般／困難兩種模式，加只跑一次的 13 個，共 63 輪，約 9 分鐘；需要 ../ticket-sim（可用 SIM_DIR 指定）
node test/run-tests.mjs --only happy,queue --mode hard   # --mode normal|hard|both，預設 both
```

端對端測試會啟動模擬站、讓 Chromium 載入真的擴充功能，每個情境除了看任務狀態，也用模擬站的統計核對：沒有重複送出、沒有替使用者按「確認建立訂單」。Playwright 預設從 `../ticket-sim/tools` 載入，可用 `PW_DIR` 指定。

情境：正常流程（停在確認頁、使用者確認後才建立訂單）、排程與開賣前預告、售完、送出時剛好被買走、剩少量、503、500 錯誤頁、送出時伺服器錯誤、表單權杖過期、讀取時請求太多（有 `Retry-After`／沒有且一直 429／頁面沒寫狀態碼）、送出時請求太多（含頁面沒寫狀態碼）、回應很慢、保留逾時提醒、驗證碼、機器人檢查、排隊（含排程倒數時遇到）、網站說資料有問題、購票人資料不完整、檢查時段與健檢、分區域時偏好的票區售完與超過預算（兩種模式）；只跑一次的流程引擎情境：沒有符合預算的選擇、場次狀態看不出來、登入逾時後繼續、送出結果不明不重送、確認頁內容不一致、暫停與繼續、中途取消、重新整理與上一頁不重做、service worker 重啟後接著走；另外 `ibon-info`（活動頁：讀取、需求比對、資料檢查、登入狀態、操作政策）、`ibon-purchase-page`（購票頁：只讀狀態、結構快照的遮罩與封閉 Shadow DOM、沒有點擊）與 `ibon-guide`（人工操作模式：建議與依據、換頁後核對、購票頁欄位標尚未驗證、填寫購票資訊頁的讀取與核對、沒有點擊）用虛構的樣本頁測；購票頁樣本的結構是假設的，通過不代表真實購票頁已經支援。

`ibon-info` 不連到真的 ibon：每個情境的測試瀏覽器都用 `--host-resolver-rules` 把 `ibon.com.tw`、`*.ibon.com.tw` 指到本機的 HTTPS 伺服器（自簽憑證，`openssl` 現場產生），並加 `--no-proxy-server`，回 `test/fixtures/` 的樣本頁（活動頁、購票頁、填寫購票資訊頁）。樣本頁內容是虛構的，只模擬讀資訊用到的結構（場次表一樣放在封閉 Shadow DOM、晚 1 秒出現；填寫購票資訊頁照真站結構快照）；測試也核對伺服器只收到 GET，沒有任何點擊或送出。

### 困難模式

模擬站開情境時加 `hard=1`（情境頁的「困難模式」連結），把真實售票網站常見的技術難點做進去。每個端對端情境都會在一般模式和困難模式各跑一次，同一支轉接要兩邊都過。

| 困難模式的難點 | 助手怎麼處理 |
|---|---|
| 沒有 `data-testid`；網站自己用的屬性名稱、元素 id、購票人欄位的 `name` 每次產生頁面都隨機換，也沒有 `autocomplete` | 用看得到的文字、欄位標籤（`label.control`）、網址定位 |
| 時段列表放在封閉的 Shadow DOM 裡，網頁的程式讀不到 | 用擴充功能才有的 `chrome.dom.openOrClosedShadowRoot` 讀 |
| 受控表單：網站以自己的資料模型為準，只改欄位的值、沒有送出事件，網站不會認 | 用原生的 value setter 設值，再送出 `input`、`change` 事件 |
| 送出要帶頁面發的表單權杖，過期就被拒絕（`tokenSec` 調時效；情境 `token-expired` 讓第一次送出一定過期） | 重新整理拿新的權杖，這一步重做一次，有次數上限 |
| 驗證碼畫在 canvas 上 | 認得出是驗證碼，停下來交給你，不讀也不填 |
| 時段列表延遲 0.3～1.5 秒才出現，只有「載入中」佔位列，沒有 `aria-busy` | 等佔位列消失、而且是新的一批時段才讀，不會讀到更新前的舊資料 |
