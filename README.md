# ibon-ticket-helper

Chrome Extension (Manifest V3)｜個人票券預訂輔助工具

## 1. 專案目標

`ibon-ticket-helper` 是一個以 Chrome Extension 為核心的個人票券預訂輔助工具，目標是協助使用者分析票券資訊、比對預訂需求、選擇場次與票種、填寫必要資料，並在適當的條件下執行預訂流程。

本專案採用可擴充的網站 Adapter、需求解析、預訂流程管理與 Policy Gate 設計，讓不同票券網站可以共用核心流程，同時保留各網站的頁面解析與操作差異。

### 1.1 產品方向

本專案的長期目標不是只有讀取和提醒，而是盡可能在合法、網站規則允許且技術上可行的範圍內，完成個人預訂流程中的重複性操作。

預期功能包含：

- 讀取活動、場次、票種、價格、剩餘時間等資訊。
- 根據使用者設定比對適合的場次與票種。
- 依照使用者設定選擇場次、票種、數量及必要選項。
- 在允許的情況下填寫預訂資料、進行頁面導覽與送出預訂。
- 在遇到需要人工判斷的情境時暫停，讓使用者接手。
- 在訂單確認或付款階段保留人工確認與操作。
- 提供倒數提醒、開賣提醒、問題回報、除錯紀錄及可重現測試案例。

上述項目是產品方向，不代表所有網站目前都已支援，也不代表每個網站都允許所有操作。實際支援程度必須依照程式碼、測試結果、網站規則與可確認的授權依據判定。

### 1.2 核心原則

1. **以使用者需求為中心**：先理解使用者要完成的預訂任務，再決定需要哪些工具與操作。
2. **可擴充**：核心流程與各網站的頁面解析、操作方式分離。
3. **可測試**：優先使用本機模擬器、測試頁面與自動化測試驗證功能。
4. **可追蹤**：重要狀態轉換、錯誤與操作結果應能被記錄和診斷。
5. **人工接手**：需要驗證、排隊處理、政策確認或其他人工判斷時，應明確暫停並提示使用者。
6. **付款由使用者操作**：不自動輸入付款驗證資料、不自動完成付款。
7. **不規避網站控制機制**：不繞過 CAPTCHA、排隊機制、反機器人檢查、購買數量限制、存取控制或速率限制。
8. **依據明確**：區分法律規定、網站服務條款、官方授權、技術限制、尚未查明的事項及開發者自行設定的限制。

| 模擬器操作 | 選擇場次、票種、數量、送出模擬訂單 | 依本機測試環境執行 |

## 5. 系統架構與設計

本專案應盡可能將核心預訂流程、網站差異、政策判斷及人工接手機制分離。

### 5.1 核心模組

以下為概念上的模組職責，實際檔案名稱及依賴關係須以現有程式碼為準。

| 模組 | 職責 |
|---|---|
| User Preferences | 儲存使用者的場次、票種、數量及其他預訂偏好 |
| Requirement Parser | 將使用者需求整理為結構化條件 |
| Site Adapter | 解析特定網站的頁面資訊及可用操作 |
| Ticket Data Parser | 擷取活動、場次、票種、價格與時間等資訊 |
| Matching Engine | 比對預訂條件並排序候選選項 |
| Workflow Engine | 管理預訂流程與狀態轉換 |
| Policy Gate | 根據網站、操作類型及確認狀態決定能否執行 |
| Human Handoff | 在需要人工處理時暫停並提示使用者 |
| Reminder Service | 管理開賣與剩餘時間提醒 |
| Diagnostic Reporter | 收集問題資訊並遮罩個人資料 |
| Test Case Converter | 將診斷資料轉換為可重現的測試案例 |

### 5.2 網站 Adapter

不同網站的 DOM、欄位、流程及狀態可能不同，因此不應將特定網站的選擇器直接散落在所有核心模組中。

Adapter 應盡可能負責：

- 判斷目前頁面類型。
- 讀取活動與票券資訊。
- 將網站特有資料轉換為統一格式。
- 判斷目前頁面狀態。
- 提供該網站支援的操作能力。
- 對未知頁面結構回報明確錯誤。
- 在無法確認狀態時避免盲目重試或繼續送出。

核心流程不應直接依賴單一網站的固定 HTML 結構。

### 5.3 Policy Gate

Policy Gate 的用途是將「功能是否已實作」與「目前是否允許執行」分開。

例如：

- 核心引擎可能已具備選擇票種的能力。
- 模擬器 Adapter 可以允許測試這個能力。
- 真實網站 Adapter 則可以依目前確認的規則限制操作。
- 當官方條款、授權或技術條件更新時，只調整受影響的規則，不必重寫整個核心引擎。

政策設定應具備可測試性，並能清楚指出操作被允許、要求確認或阻擋的具體原因。

不可用模糊的全域判斷取代各項操作的獨立評估。

## 6. 預訂流程與狀態管理

預訂流程應使用明確的狀態管理，避免頁面尚未準備好、資料不完整或狀態不明時就繼續操作。

概念上的流程如下：

1. 取得使用者需求。
2. 解析場次、票種、數量及其他條件。
3. 讀取目前活動與頁面資訊。
4. 驗證資料完整性。
5. 比對候選場次與票種。
6. 依目前網站政策與 Adapter 能力判斷可執行的操作。
7. 執行已允許的操作。
8. 驗證操作結果與下一個頁面狀態。
9. 遇到未知狀態、人工驗證或政策限制時暫停。
10. 在需要時交由使用者接手。
11. 到達訂單檢查或確認階段時，讓使用者確認。
12. 付款由使用者自行操作。

以上為流程設計原則，不代表目前所有狀態都已完整實作。Claude Code 應檢查現有狀態機、測試及實際 Adapter 後，再更新本節。

### 6.1 操作結果必須驗證

不能只因為按鈕點擊成功，就認定預訂操作成功。

應依網站實際行為確認：

- 是否已選取正確場次。
- 是否已選取正確票種。
- 數量是否符合使用者設定與網站限制。
- 是否出現錯誤訊息。
- 是否跳轉到預期頁面。
- 是否需要人工確認或驗證。
- 目前訂單狀態是否能被可靠辨識。

如果無法確定操作結果，應停止繼續操作並回報原因，不可假設成功。

## 7. ibon Adapter 與真實網站驗證

### 7.1 目前政策設定

| 選擇票種及數量 | 目前不自動執行 |

| 付款 | 使用者自行操作 |

這張表描述目前的實作與設定。未來如需變更，應先針對具體操作確認規則與依據，再修改相關 Policy、Adapter 和測試。

## 8. 倒數提醒與開賣提醒

### 8.1 剩餘時間提醒

`0.8.0` 的既有紀錄指出，已實作讀取頁面剩餘時間並通知使用者的功能。

已記錄的行為：

- 讀取可辨識的剩餘時間資訊。
- 每 10 秒檢查一次。
- 在剩餘 2 分鐘與 1 分鐘時各提醒一次。
- 同一輪倒數不重複發送相同提醒。
- 使用 `chrome.alarms` 支援背景分頁情境。
- 如果倒數停止、跳動異常或資訊不存在，顯示未知狀態，不猜測剩餘時間。

實際的頁面匹配規則、排程機制與測試覆蓋範圍，應以目前程式碼為準。

### 8.2 開賣提醒

已記錄的行為：

- 根據活動的開賣時間設定提醒。
- 使用台灣時區處理時間。
- 開賣前 5 分鐘與 1 分鐘各提醒一次。
- 若時間只有日期、時間已過或無法可靠解析，標記為未知，不任意建立排程。
- 提醒本身不會自動開啟頁面、刷新頁面或執行購買。

修改提醒功能時，應測試時區、跨日、無效日期、重複排程、取消排程及背景分頁等情境。

## 10. 測試策略

本專案至少需要區分以下測試層級。

### 10.1 單元測試

測試需求解析、資料驗證、時間處理、政策判斷、狀態轉換、提醒排程與資料遮罩等獨立邏輯。

### 10.2 模擬器整合測試

在 `ticket-sim` 環境測試網站 Adapter、頁面解析、場次與票種選擇、流程狀態及錯誤處理。

### 10.3 Extension 端對端測試

驗證 Chrome Extension 的使用者介面、背景排程、頁面互動及完整工作流程。

### 10.4 真實網站相容性驗證

僅在適當條件下確認真實網站的唯讀解析、頁面相容性及人工接手流程。對尚未確認或不允許的自動操作，不得因為模擬器測試成功就直接在真實網站啟用。

### 10.5 測試報告

每次修改後應回報：

- 執行的實際指令。
- 通過、失敗及略過的測試數量。
- 失敗測試的原因。
- 是否新增或修改測試。
- 是否有未驗證的真實網站相容性問題。

不要捏造測試數字，也不要把之前的測試結果當成這次修改後的結果。

## 13. 新增網站或功能的開發流程

### Step 1：理解需求

先明確列出使用者希望完成的任務、輸入資料、預期結果及人工接手點。

### Step 2：檢查現有實作

確認核心流程、Adapter、Policy Gate、測試與使用者介面是否已有可重用的功能。

### Step 3：確認操作邊界

將功能分為：

- 可直接進行的本機開發。
- 可在模擬器中測試的自動化。
- 可在真實網站執行的唯讀功能。
- 需要額外確認規則或授權的真實網站操作。
- 必須由使用者自行處理的驗證、付款或其他受限制操作。

### Step 4：設計最小變更

優先沿用現有架構，避免不必要的大規模重構。

### Step 5：實作與測試

先建立或更新測試，再實作功能；或在現有測試架構下補上必要的回歸測試。

### Step 6：回報結果

提供實際修改檔案、功能差異、測試結果、限制及下一步。
